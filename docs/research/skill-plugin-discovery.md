# Cross-client skill and plugin discovery

Research for [agentlens #43](https://github.com/asmundwien/agentlens/issues/43), captured 2026-09-02.

## Scope and evidence

This report covers the installed clients on the inspected workstation: OMP 18.1.2, Claude Code 2.1.241, Codex CLI 0.144.1, and Pi 0.80.2. It combines:

- first-party documentation and source at the installed release where available;
- direct, non-mutating inspection of the clients' configuration and package trees; and
- read-only CLI probes (`--version`, help, list/details/config/doctor commands, and OMP `skill://` reads).

No skill, plugin, configuration, or cache was changed. Credential-bearing files were not copied into this report.

## Short answer

`~/.agents/skills` and project `.agents/skills` are the only skill roots that OMP, Codex, and Pi all discover natively. Claude Code does **not** document either root: it uses `~/.claude/skills` and project `.claude/skills`. A shared directory can therefore preserve all four clients only through supported per-skill links into Claude's roots, or through explicit client configuration. It must use the strict Agent Skills shape `<root>/<name>/SKILL.md`, keep `name` equal to the directory name, include `description`, and avoid relying on client-specific frontmatter. OMP's one-level scan is the narrowest layout constraint. These are compatibility limits, not a decision about which location should be canonical. [Agent Skills specification](https://agentskills.io/specification#directory-structure); [OMP skills](https://github.com/can1357/oh-my-pi/blob/v18.1.2/docs/skills.md#required-layout-and-skillmd-expectations); [Claude skills](https://code.claude.com/docs/en/skills#where-skills-live); [Codex skills](https://developers.openai.com/codex/skills#where-to-save-skills); [Pi 0.80.2 skills](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/docs/skills.md#locations)

Plugin stores are not interchangeable. Claude uses `.claude-plugin/plugin.json` and its own registry/cache; Codex uses `.codex-plugin/plugin.json` and marketplace state in `~/.codex`; OMP has an OMP/Claude-compatible marketplace plus OMP package manifests; Pi distributes extensions and skills as Pi packages declared in `package.json`. A plugin cache is materialized client state, not an author-owned source directory. [Claude plugin structure](https://code.claude.com/docs/en/plugins-reference#plugin-directory-structure); [Codex plugin packaging](https://developers.openai.com/plugins/build/plugins#plugin-structure); [OMP marketplace](https://github.com/can1357/oh-my-pi/blob/v18.1.2/docs/marketplace.md#concepts); [Pi packages](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/docs/packages.md#pi-packages)

## Why this OMP session sees the skills it sees

The session had all OMP skill source toggles enabled, no `skills.customDirectories`, and no `disabledExtensions` entries. There were no project skill roots in the agentlens checkout, no `~/.omp/agent/skills`, no OMP marketplace plugins, and no managed OMP skills. OMP 18.1.2 orders providers by priority and then keeps the first occurrence of each skill name: native `.omp` (100), OMP plugin packages (90), Claude standalone (80), then Claude plugin cache, `.agent[s]`, and Codex (70 in that registration order), followed by lower-priority providers. Custom directories are a later override, and identical files are deduplicated by real path. [OMP provider order and collision rules](https://github.com/can1357/oh-my-pi/blob/v18.1.2/docs/skills.md#built-in-skill-providers-and-precedence); [OMP 18.1.2 loader](https://github.com/can1357/oh-my-pi/blob/v18.1.2/packages/coding-agent/src/extensibility/skills.ts#L117-L263)

Two read-only probes make the collision behavior concrete:

- `skill://tdd` returned the 109-line standalone `~/.claude/skills/tdd/SKILL.md`, not the distinct 38-line plugin copy. This matches Claude provider priority 80 over Claude-plugin priority 70.
- `~/.claude/skills/unslop` is a directory symlink to `../../.agents/skills/unslop`; `realpath` resolves both names to the same directory. OMP exposes one `unslop`.

Some discovered skills are intentionally absent from the system prompt when their metadata disables model invocation; OMP still retains hidden skills for explicit `skill://` or slash-command use. [OMP runtime exposure](https://github.com/can1357/oh-my-pi/blob/v18.1.2/docs/skills.md#system-prompt-exposure)

### Disabled Claude plugin cache disagreement

Direct state inspection showed:

1. `~/.claude/plugins/installed_plugins.json` still records `frontend-design@claude-plugins-official` and its cached install path.
2. `~/.claude/settings.json` has no `enabledPlugins` entry for it, while `claude plugin list` reports it as **disabled** and `claude plugin details frontend-design@claude-plugins-official` reports it as not found.
3. The active OMP prompt nevertheless lists `frontend-design`, and `skill://frontend-design` returns the content of that cached plugin skill.

Claude's documented contract is that disabled plugins do not supply active plugin skills; disable/uninstall plus reload or restart removes those skills from Claude's active set. Cached bytes may remain because old/orphaned plugin versions have a roughly 14-day grace period. [Claude remove/disable behavior](https://code.claude.com/docs/en/skills#remove-a-skill); [Claude plugin caching](https://code.claude.com/docs/en/plugins-reference#plugin-caching-and-file-resolution)

OMP's 18.1.2 compatibility loader explains the mismatch: it rejects an installed entry only when the registry has `entry.enabled === false` or merged Claude settings contain an explicit `enabledPlugins[plugin-id] === false`; absence is treated as enabled for a user-scoped cache entry. Claude 2.1.241 treats this absent entry as disabled on this machine. Thus OMP's source and its observed behavior agree with each other but disagree with Claude's effective activation state. [OMP 18.1.2 cache-root selection](https://github.com/can1357/oh-my-pi/blob/v18.1.2/packages/coding-agent/src/discovery/helpers.ts#L1018-L1141)

This matters operationally: deleting or editing the cache would fight Claude's plugin manager and is outside this research. The safe conclusion is only that a retained Claude cache entry is not proof of enablement, while OMP 18.1.2 can currently mistake it for one.

## Client-by-client rules

### OMP 18.1.2

**Skills.** Native user skills are under the active profile's agent directory, normally `~/.omp/agent/skills`. Native project `.omp/skills` roots are scanned from CWD upward, closest first. OMP additionally imports user/project Claude roots, user/project `.agent` and `.agents` roots, `~/.codex/skills` plus CWD `.codex/skills`, compatible Claude plugin caches, installed OMP plugin packages, `.github/skills`, and managed skills. All provider and custom-directory roots use a non-recursive one-child layout. [Native provider source](https://github.com/can1357/oh-my-pi/blob/v18.1.2/packages/coding-agent/src/discovery/builtin.ts#L290-L344); [OMP skills documentation](https://github.com/can1357/oh-my-pi/blob/v18.1.2/docs/skills.md#discovery-pipeline)

**Precedence and shadowing.** Provider priority wins before user/project level. Within native project roots, nearer CWD appears first; the user native root comes after project scans at the same priority. Across the full provider list, first name wins; identical targets are silently deduplicated by `realpath`. Custom-directory entries override provider entries, first custom directory wins among duplicates, and managed skills are last. Filters can disable whole sources, exact skill names through `disabledExtensions`, and include/ignore globs. [Native ordering](https://github.com/can1357/oh-my-pi/blob/v18.1.2/packages/coding-agent/src/discovery/builtin.ts#L290-L321); [aggregation and filters](https://github.com/can1357/oh-my-pi/blob/v18.1.2/packages/coding-agent/src/extensibility/skills.ts#L117-L300)

**Symlinks.** The scanner accepts directory symlinks as child candidates and checks for `SKILL.md`; the aggregator canonicalizes loaded files before duplicate handling. A broken link has no existing `SKILL.md` and is skipped. [OMP scanner](https://github.com/can1357/oh-my-pi/blob/v18.1.2/packages/coding-agent/src/discovery/helpers.ts#L377-L441)

**Plugins and update ownership.** OMP marketplace installs are copied/cached and registered under the OMP plugin data root, normally `~/.omp/plugins`; project installs use the nearest project `.omp/plugins`. Enabled project installs shadow the same user plugin, but a disabled project install does not. OMP's marketplace/plugin commands own install, enable/disable, upgrade, cache invalidation, and lock/registry state. A marketplace catalog refresh does not reinstall plugins. Plugin changes require `/reload-plugins` for skills/commands/MCP and a restart for initialized tools, hooks, or extension modules. Local linked packages remain author-owned. [OMP marketplace scopes, updates, and layout](https://github.com/can1357/oh-my-pi/blob/v18.1.2/docs/marketplace.md#updates-removal-and-scope); [OMP extension loading](https://github.com/can1357/oh-my-pi/blob/v18.1.2/docs/extension-loading.md#inputs-to-extension-loading)

### Claude Code 2.1.241

**Skills.** Claude loads enterprise-managed, personal `~/.claude/skills/<name>/SKILL.md`, project `.claude/skills/<name>/SKILL.md`, and enabled plugin skills. At startup it checks the launch directory and parents through repository root. Nested `.claude/skills` below CWD load lazily after Claude reads or edits in that subtree. `--add-dir` skill discovery is supported when the project setting source is enabled. The currently documented `/cd` discovery behavior requires Claude Code 2.1.246, so it must not be attributed to installed 2.1.241. [Claude locations and discovery](https://code.claude.com/docs/en/skills#where-skills-live); [Claude parent/nested discovery](https://code.claude.com/docs/en/skills#discovery-from-parent-and-nested-directories)

**Precedence and shadowing.** Enterprise overrides personal, personal overrides project, and any of those overrides a same-name bundled skill. A skill also beats a same-name legacy command. Plugin skills are namespaced `plugin-name:skill-name`, so they coexist rather than shadowing standalone skills. Nested duplicate skills remain available under directory-qualified names; the project-root copy owns the unqualified name. Local, plugin, bundled, command, and MCP names all beat a same-name skill synced from claude.ai. [Claude conflict rules](https://code.claude.com/docs/en/skills#where-skills-live)

**Symlinks.** A personal/project skill-name entry may link to a directory; Claude follows it and loads a repeated target once. Plugin copying is stricter: links inside the plugin are preserved, links elsewhere in the same marketplace are dereferenced into the cache, and links outside the marketplace are skipped. `--plugin-dir`, local-path, and copy-mode plugins preserve only links whose targets stay inside the plugin. [Claude skill links](https://code.claude.com/docs/en/skills#where-skills-live); [Claude plugin link rules](https://code.claude.com/docs/en/plugins-reference#share-files-within-a-marketplace-with-symlinks)

**Plugins, disabled cache, and updates.** Marketplace plugins are copied to `~/.claude/plugins/cache`; activation comes from scoped `enabledPlugins` state, not mere cache presence. User choices persist across updates and reinstalls. Previous versions remain temporarily as orphaned cache directories, and Claude Glob/Grep skip them. `claude plugin update` and marketplace auto-update own copied versions; `${CLAUDE_PLUGIN_ROOT}` can change on update. `/reload-plugins` switches skills, hooks, MCP, and LSP paths; monitors need restart. A skills-directory plugin is discovered in place and has no install/update step, so its author owns its files. [Claude default/explicit activation](https://code.claude.com/docs/en/plugins-reference#default-enabled-state); [cache lifecycle](https://code.claude.com/docs/en/plugins-reference#plugin-caching-and-file-resolution); [update behavior](https://code.claude.com/docs/en/plugins-reference#plugin-update); [skills-directory plugins](https://code.claude.com/docs/en/plugins-reference#skills-directory-plugins)

### Codex CLI 0.144.1

**Skills.** Current official documentation defines repository `.agents/skills` roots from CWD through repository root, user `$HOME/.agents/skills`, admin `/etc/codex/skills`, and bundled system skills. Codex follows linked skill directories. Same-name skills are not merged; both may appear in selectors. Local disable rules use `[[skills.config]]` with a `path` and `enabled = false`. [Codex local skill roots, duplicates, links, and disabling](https://developers.openai.com/codex/skills#where-codex-loads-local-skills)

The inspected installation also contains `~/.codex/skills`, including `.system` and `figma-implement-design`. This is a legacy compatibility root, not the user root advertised by current docs. Current Codex source still labels `$CODEX_HOME/skills` as deprecated while adding `$HOME/.agents/skills`, system, plugin, extra, and repository roots. The OMP session's `figma-implement-design` came from this legacy root because OMP explicitly scans it. [Codex root resolver](https://github.com/openai/codex/blob/984a4f2dc9e50f6645b8fe04a91570876f8d3c83/codex-rs/ext/skills/src/host_roots.rs#L47-L156); [OMP Codex provider](https://github.com/can1357/oh-my-pi/blob/v18.1.2/packages/coding-agent/src/discovery/codex.ts#L207-L234)

**Plugins and disabled cache.** Installed 0.144.1 exposes `codex plugin add/list/remove` and `codex plugin marketplace add/list/upgrade/remove`. Its read-only list showed installed enabled plugins under `openai-primary-runtime` and `openai-bundled`, while many marketplace bundles were present on disk but reported `not installed`. The inspected `~/.codex/config.toml` had explicit `[plugins."name@marketplace"] enabled = true` entries. This matches the official rule: marketplace content is copied under `~/.codex/plugins/cache/<marketplace>/<plugin>/<version>`, while enabled/disabled state is stored separately in `~/.codex/config.toml`. Cached or marketplace-present bytes alone therefore do not activate a plugin. [Codex local marketplaces and activation](https://developers.openai.com/plugins/build/plugins#how-local-marketplaces-work); [Codex CLI plugin browser](https://developers.openai.com/codex/plugins#plugin-directory-in-codex-cli)

**Update ownership and limits.** Codex/ChatGPT owns installed cache copies and config state. `codex plugin marketplace upgrade` refreshes configured Git marketplace snapshots; add/remove or the plugin browser controls installation, and a new session is required before newly installed bundled skills/tools are used. A local marketplace's source tree remains author-owned, but the host loads the installed cached copy. The public docs do not specify a same-name winner between standalone and plugin skills for 0.144.1, so no precedence is claimed beyond standalone duplicates coexisting and disabled plugins contributing nothing. [Codex marketplace commands](https://developers.openai.com/plugins/build/plugins#add-a-marketplace-from-the-cli); [Codex plugin activation](https://developers.openai.com/codex/plugins#plugin-directory-in-codex-cli)

### Pi 0.80.2

**Skills.** Pi loads global `~/.pi/agent/skills` and `~/.agents/skills`; trusted-project `.pi/skills` and `.agents/skills` from CWD through git root (or filesystem root outside a repo); package `skills` resources; settings paths; and repeatable `--skill` paths. It recursively finds directories containing `SKILL.md`. Native `.pi` roots also accept direct root Markdown files; `.agents/skills` roots do not. `--no-skills` disables ambient discovery but explicit `--skill` still loads. [Pi 0.80.2 skills documentation](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/docs/skills.md#locations)

**Precedence and shadowing.** Installed source assigns resource ranks, highest first: project settings entry, project auto-discovery, user settings entry, user auto-discovery, then package resource. Enabled paths are passed in that order to a name-keyed skill map; the first name wins and later collisions warn. CLI extension-package skill roots are prepended, while explicit skill paths remain additive; `--no-skills` leaves only explicit inputs. This package-manager ordering is more specific than the low-level `loadSkills({ includeDefaults: true })` helper, whose direct defaults are user then project; the CLI uses the package manager and calls the helper with `includeDefaults: false`. [Pi 0.80.2 package-manager precedence](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/src/core/package-manager.ts#L49-L65); [installed resource loader equivalent](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/src/core/resource-loader.ts#L229-L286); [first-name-wins loader](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/src/core/skills.ts#L400-L490)

**Symlinks.** Pi follows directory and file links, skips broken links, and recursively scans their targets. It canonicalizes the `SKILL.md` path and silently deduplicates the same file reached through aliases before checking name collisions. The installed changelog explicitly records the `~/.pi/agent/skills -> ~/.agents/skills` alias case. [Pi 0.80.2 skill loader](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/src/core/skills.ts#L114-L206); [canonical dedup](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/src/core/skills.ts#L400-L450)

**Packages, disabled material, and updates.** Pi calls its distributable bundles packages. User npm/git installs live under `~/.pi/agent/{npm,git}`, project installs under `.pi/{npm,git}`, and local path packages are read in place. `pi config` enables/disables individual package and local resources; disabled resources remain represented in resolution metadata but are filtered before skill loading. Pi does not document a separate plugin-cache discovery rule: retained package bytes are not sufficient for activation. `pi update` updates Pi itself, `pi update --extensions` updates packages, and `pi update --all` does both. Exact npm versions and pinned Git refs do not float; local paths remain author-owned. [Pi package filtering and activation](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/docs/packages.md#package-filtering); [Pi package sources and updates](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/docs/packages.md#install-and-manage)

## Shared-directory compatibility envelope

A shared authored skill set can preserve discovery behavior only if all of these remain true:

1. **Flat root:** every skill is exactly `<root>/<skill-name>/SKILL.md`. Pi and Codex can scan deeper arrangements, but OMP cannot. [OMP scanner contract](https://github.com/can1357/oh-my-pi/blob/v18.1.2/docs/skills.md#directory-layout)
2. **Strict Agent Skills metadata:** `name` and `description` are present, the name uses the standard character/length rules, and it matches its parent directory. Pi deliberately allows name/directory mismatch, and OMP permits missing descriptions for some foreign providers, but those leniencies are not portable. [Agent Skills frontmatter](https://agentskills.io/specification#frontmatter); [Pi compatibility note](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/docs/skills.md#skills)
3. **No semantic dependence on extensions:** Claude-specific fields such as subagent execution or dynamic shell/context injection, OMP `hide`/`globs`, and host-specific `allowed-tools` interpretations may be ignored or behave differently elsewhere. The Agent Skills specification marks `allowed-tools` experimental. [Agent Skills `allowed-tools`](https://agentskills.io/specification#allowed-tools-field); [Claude cross-host note](https://code.claude.com/docs/en/skills#using-skill-frontmatter-outside-claude-code)
4. **Supported links only:** OMP, Claude, Codex, and Pi all follow ordinary linked skill directories, and OMP/Pi canonicalize repeat targets. Plugin-internal links have separate containment rules and should not be used as a general cross-client bridge. [OMP scanner](https://github.com/can1357/oh-my-pi/blob/v18.1.2/packages/coding-agent/src/discovery/helpers.ts#L377-L441); [Claude links](https://code.claude.com/docs/en/skills#where-skills-live); [Codex links](https://developers.openai.com/codex/skills#where-codex-loads-local-skills); [Pi links](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/src/core/skills.ts#L114-L206)
5. **Avoid duplicate names:** Claude standalone levels shadow, OMP and Pi keep one first winner, while Codex can show both. A duplicate may therefore select different content by client. [Claude conflicts](https://code.claude.com/docs/en/skills#where-skills-live); [OMP conflicts](https://github.com/can1357/oh-my-pi/blob/v18.1.2/docs/skills.md#collision-and-duplicate-handling); [Codex duplicates](https://developers.openai.com/codex/skills#where-codex-loads-local-skills); [Pi collisions](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/docs/skills.md#validation)
6. **Do not canonicalize a client cache:** cache paths are versioned, client-owned, may retain disabled/orphaned material, and may change on update. Author-owned source plus supported discovery links/configuration is the portable boundary. [Claude cache lifecycle](https://code.claude.com/docs/en/plugins-reference#plugin-caching-and-file-resolution); [Codex local cache](https://developers.openai.com/plugins/build/plugins#how-local-marketplaces-work); [OMP on-disk layout](https://github.com/can1357/oh-my-pi/blob/v18.1.2/docs/marketplace.md#on-disk-layout); [Pi local paths](https://github.com/earendil-works/pi/blob/v0.80.2/packages/coding-agent/docs/packages.md#local-paths)

## Reconciled disagreements and remaining uncertainty

- **Confirmed disagreement:** OMP 18.1.2 exposes a Claude plugin skill from a cache entry that Claude 2.1.241 reports disabled. OMP source explains the observed absent-setting/implicit-enable mismatch.
- **Documentation drift:** Claude's current documentation includes `/cd` skill discovery introduced in 2.1.246; the installed 2.1.241 does not get that claim. Other documented conflict and symlink behavior applies to this installed version unless the docs state a later gate.
- **Legacy Codex root:** current Codex docs direct users to `~/.agents/skills`, while current source and the installed tree retain deprecated `$CODEX_HOME/skills`. OMP explicitly imports that legacy root. It should not be treated as Codex's forward-looking shared user location.
- **Codex plugin precedence:** installed commands and state verify plugin install/enable/cache behavior, but public documentation does not define a same-name winner between plugin and standalone skills for CLI 0.144.1. This report leaves it unspecified.
- **Pi terminology:** there is no independent Pi “plugin cache” contract. Pi package resource enablement and update ownership are documented and visible in installed source; inferring Claude-style orphan-cache behavior would be wrong.
