# Claude Code installed-skill inventory surfaces

**Research date:** 2026-08-23  
**Decision boundary:** Claude Code **v2.1.241**, the GitHub release marked **Latest** on the research date, tag commit [`45bdfa96ca415da92e62b6ca85a1d6e29adf3c44`](https://github.com/anthropics/claude-code/commit/45bdfa96ca415da92e62b6ca85a1d6e29adf3c44) ([release](https://github.com/anthropics/claude-code/releases/tag/v2.1.241), [tag ref](https://api.github.com/repos/anthropics/claude-code/git/ref/tags/v2.1.241)). Anthropic documents `latest` as the default channel and `stable` as typically about one week behind while skipping major regressions, so “supported” is not one immutable version across installations ([release-channel documentation](https://code.claude.com/docs/en/setup#configure-release-channel)).

## Decision

Claude Code has supported **session-scoped views** of discovered skills and a supported **usage-event** surface, but no documented passive API that returns the complete effective installed-skill inventory on a Mac.

Agentlens should therefore:

1. Treat the Agent SDK `system/init.skills` and `system/init.slash_commands` fields as a **current-session, currently-discovered advertisement**, not a workstation inventory. The skills array includes user-invocable and bundled skills but omits a loaded skill with `user-invocable: false`; `slash_commands` also mixes built-ins, bundled skills, user skills, legacy command files, and MCP prompts ([Agent SDK skill confirmation](https://code.claude.com/docs/en/agent-sdk/skills#confirm-skills-loaded), [available commands](https://code.claude.com/docs/en/agent-sdk/skills#discover-available-commands)).
2. Use `claude_code.skill_activated` for Claude Code usage events when OTel is available. It reports the skill name, trigger, source, and optional plugin/marketplace attribution for both user slash invocation and model invocation ([OTel event contract](https://code.claude.com/docs/en/monitoring-usage#skill-activated-event)). The complete trigger contract for user slash, model-proactive, and nested invocation dates from [v2.1.126](https://github.com/anthropics/claude-code/releases/tag/v2.1.126).
3. Never label a filesystem scan, `/skills` view, SDK init message, plugin list, or OTel stream as a complete installed-skill inventory. Record the Claude Code version, launch directory, added directories, session phase, and known policy/configuration constraints with each observation.
4. If Agentlens later scans source directories, label the result **candidate installations inferred from documented locations**, not effective installed skills. Claude Code’s lazy nested discovery, source precedence, settings, trust, plugin state, and managed policy cannot all be reproduced from a passive scan using a documented resolver API.

## Source discovery and inventory gaps

| Source | Source-owned discovery and visibility rules | Why a passive inventory is incomplete |
| --- | --- | --- |
| **Enterprise** | Enterprise skills live under the managed-settings location and apply organization-wide. The documented conflict order is enterprise over personal over project ([skill locations and precedence](https://code.claude.com/docs/en/skills#where-skills-live)). On macOS the managed-settings base is `/Library/Application Support/ClaudeCode/` ([managed delivery paths](https://code.claude.com/docs/en/managed-settings#deploy-a-managed-settings-file)). | A local process may lack permission to inspect the managed directory; remote server-managed policy can affect the session; the documented session surfaces do not provide an enterprise skill catalog. |
| **Personal** | `~/.claude/skills/<name>/SKILL.md` applies across projects. Symlinked skill directories are followed and the same target reached from more than one location loads once ([locations and symlinks](https://code.claude.com/docs/en/skills#where-skills-live)). | Presence on disk does not prove visibility: managed policy, `skillOverrides`, safe/bare mode, name conflicts, or invalid content can change the effective set. |
| **Project and ancestors** | Claude Code loads `.claude/skills/` from the launch directory and each ancestor up to the repository root ([parent discovery](https://code.claude.com/docs/en/skills#discovery-from-parent-and-nested-directories)). Project skills lose same-name conflicts to personal and enterprise skills but override bundled skills ([precedence](https://code.claude.com/docs/en/skills#where-skills-live)). | The effective set depends on the launch directory and repository boundary. A workstation-wide scan cannot identify which project set applies without a session context. |
| **Added directory** | `--add-dir` and `/add-dir` are exceptions to the normal file-access-only rule: they load `.claude/skills/` and `.claude/commands/` from each added directory. `permissions.additionalDirectories` grants access but does **not** load those artifacts ([additional-directory skills](https://code.claude.com/docs/en/skills#skills-from-additional-directories)). The SDK’s `additionalDirectories`/`add_dirs` options use this same path ([SDK discovery note](https://code.claude.com/docs/en/agent-sdk/skills#how-skills-work-with-the-agent-sdk)). | Added directories are launch/session inputs, and `/add-dir` can change them during a session. They are not derivable from ordinary project files alone. |
| **Plugin** | An enabled plugin automatically discovers `skills/`, `commands/`, or a root `SKILL.md`; plugin skills are namespaced as `plugin-name:skill-name` ([plugin skill layout](https://code.claude.com/docs/en/plugins-reference#skills)). Plugins may be user, project, local, or managed scope, or loaded for one session through `--plugin-dir`/`--plugin-url` ([plugin scopes](https://code.claude.com/docs/en/plugins-reference#installation-scopes), [CLI plugin flags](https://code.claude.com/docs/en/cli-reference#cli-flags)). | `claude plugin list --json` is machine-readable but is a plugin inventory, not an effective skill inventory. Session-only flags must be repeated for them to appear, and the per-plugin component view is separate ([plugin-list contract](https://code.claude.com/docs/en/plugins-reference#plugin-list)). |
| **Skills-directory plugin** | A child of a skills directory containing `.claude-plugin/plugin.json` becomes `<name>@skills-dir` on the next session. A project-scoped instance loads only from the `.claude/skills/` of the directory where Claude Code starts; unlike plain project skills, it does not walk ancestors. It also requires workspace trust ([skills-directory plugins](https://code.claude.com/docs/en/plugins-reference#skills-directory-plugins)). | A scan that applies plain-skill ancestor rules to these plugins will overcount. Trust and launch directory affect whether the plugin—and therefore its skills—is active. |
| **Synced from claude.ai** | In ordinary local sessions, account-enabled skills download only during a non-interactive run with `CLAUDE_CODE_SYNC_SKILLS=1`; they persist in `~/.claude/skills/synced/` and later local sessions load them. Changes require another explicit sync. `/skills` groups them under `claude.ai sync` ([local sync procedure](https://code.claude.com/docs/en/skills#where-synced-skills-load)). `syncClaudeAiSkills: false` blocks downloads and hides already-synced skills; `true` does not enable syncing ([setting contract](https://code.claude.com/docs/en/settings-reference#syncclaudeaiskills)). | Disk state can be stale relative to the account. Account state is not exposed as a passive local catalog. Cowork/cloud sync at session start and do not read the Mac’s personal skill directory, so remote and local inventories differ ([Cowork/cloud rules](https://code.claude.com/docs/en/skills#skills-in-cowork-and-cloud-sessions)). |
| **Bundled** | Bundled skills ship with Claude Code and are available in sessions unless disabled. The current commands reference marks bundled entries as **Skill**; `disableBundledSkills` removes them except for the documented `/doctor` exception ([bundled skills](https://code.claude.com/docs/en/skills#bundled-skills), [setting](https://code.claude.com/docs/en/settings-reference#disablebundledskills)). | The set is version-dependent and can be shadowed. A source scan cannot see prompt artifacts embedded in the binary, while command lists also contain non-skill built-ins. |
| **Legacy custom command** | `.claude/commands/<name>.md` remains supported and behaves like a skill command. A same-name `SKILL.md` wins. Added directories also load their command files, while plugin `commands/` is another plugin skill source ([custom-command compatibility and precedence](https://code.claude.com/docs/en/skills#where-skills-live), [SDK command sources](https://code.claude.com/docs/en/agent-sdk/skills#commands-in-agent-sdk-sessions)). | The SDK `slash_commands` field does not distinguish every entry’s backing artifact. Treating every advertised slash command as an installed skill would count built-ins and MCP prompts. |
| **Lazy nested project skill** | Descendant `.claude/skills/` directories are not loaded at startup. A nested set appears after Claude first reads or edits a file in that subtree and stays available for the session. A conflict coexists under a directory-qualified name such as `apps/web:deploy`, while the root skill keeps `/deploy` ([nested discovery and naming](https://code.claude.com/docs/en/skills#discovery-from-parent-and-nested-directories)). This behavior was introduced in [v2.1.178](https://github.com/anthropics/claude-code/releases/tag/v2.1.178). | No startup snapshot can contain not-yet-traversed descendants. Two sessions in the same directory can have different currently-discovered sets because their file traversal differs. |

## Resolution and visibility rules

The following are supported current rules, not Agentlens inferences:

- Same-name plain skills resolve **enterprise → personal → project**. Any of those levels can replace a same-name bundled skill, but a bundled alias remains bound to the bundled skill ([conflict rules](https://code.claude.com/docs/en/skills#where-skills-live)).
- Plugin skills use a namespace and coexist with plain skills. For plugin skills, frontmatter `name` controls the final namespaced segment; personal/project plain skills use the directory name as the invocation name ([command-name rules](https://code.claude.com/docs/en/skills#how-a-skill-gets-its-command-name)).
- `SKILL.md` wins over a same-name legacy `.claude/commands/*.md`. Any built-in, bundled, local, plugin, command-file, or MCP-prompt collision causes the same-name synced skill to be skipped ([synced collision rules](https://code.claude.com/docs/en/skills#when-a-synced-skill-name-matches-another-command)). Synced-skill shadowing and local dynamic expansion were hardened in [v2.1.228](https://github.com/anthropics/claude-code/releases/tag/v2.1.228).
- `disable-model-invocation: true` makes a skill user-only and removes its description from Claude’s context; `user-invocable: false` makes it model-only and removes it from the `/` menu. Full content remains lazy until invocation ([invocation controls](https://code.claude.com/docs/en/skills#control-who-invokes-a-skill)).
- `skillOverrides` provides `on`, `name-only`, `user-invocable-only`, and `off`; absent means `on`. It does not apply to plugin skills. Since v2.1.199, `off` also removes the skill from advertised Remote Control and Agent SDK command lists ([visibility override contract](https://code.claude.com/docs/en/skills#override-skill-visibility-from-settings)).
- `--bare` skips normal skill, command, plugin, hook, and settings-source discovery, but still loads skills—not command files—from a directory passed with `--add-dir`; `--safe-mode` disables all custom skills and related customizations ([bare mode](https://code.claude.com/docs/en/headless#start-faster-with-bare-mode), [safe-mode flag](https://code.claude.com/docs/en/cli-reference#cli-flags)).

These rules mean “installed” and “visible now” are different facts. Agentlens should preserve the client-specific installation where observed, but must attach a visibility qualifier rather than infer skill adoption from absence in one session.

## Supported observation surfaces

| Surface | What it reliably exposes | Material gaps |
| --- | --- | --- |
| **`/skills`** | Interactive current-session skill management; it can write `skillOverrides` for applicable non-plugin skills, and labels synced entries ([visibility UI](https://code.claude.com/docs/en/skills#override-skill-visibility-from-settings), [synced labels](https://code.claude.com/docs/en/skills#when-a-synced-skill-name-matches-another-command)). | Not passive or machine-readable; session-, directory-, policy-, and lazy-discovery-dependent. Plugin visibility is managed through `/plugin`, not `skillOverrides`. |
| **`/` autocomplete and `/context`** | The `/` menu advertises currently available user-invocable commands; `/context` identifies synced skills as `claude.ai sync` ([synced labels](https://code.claude.com/docs/en/skills#when-a-synced-skill-name-matches-another-command)). | Human UI; command list is not skill-only; model-only and not-yet-lazy-loaded skills are absent. |
| **Agent SDK `system/init`** | `skills` lists discovered user-invocable skills plus bundled skills. `slash_commands` lists dispatchable non-terminal commands and includes user skills, bundled skills, built-ins, legacy commands, and possibly MCP prompts ([SDK init skills](https://code.claude.com/docs/en/agent-sdk/skills#confirm-skills-loaded), [SDK command list](https://code.claude.com/docs/en/agent-sdk/skills#discover-available-commands)). | `skills` omits `user-invocable: false`; it reflects discovery, not the SDK `skills` allowlist; neither field is documented as a complete source-attributed effective inventory. Lazy nested entries cannot appear before traversal. |
| **`claude plugin list --json` and `claude plugin details`** | Installed plugin version/source/enable state, plus per-plugin component details. Skills-directory, synced, and flag-loaded plugins have explicit listing caveats ([plugin list](https://code.claude.com/docs/en/plugins-reference#plugin-list), [component details](https://code.claude.com/docs/en/discover-plugins#manage-installed-plugins)). | Covers plugins, not plain, bundled, enterprise, synced-skill, or legacy-command inventory. It does not resolve session skill precedence. |
| **Hooks** | `UserPromptExpansion` observes a user-typed command after resolution and reports `command_name`, arguments, source, and original prompt. A `PreToolUse` hook on `Skill` covers model calls; `ConfigChange` can match source `skills`; `DirectoryAdded` reports additions ([expansion hook](https://code.claude.com/docs/en/hooks#userpromptexpansion), [matcher values](https://code.claude.com/docs/en/hooks#matcher-patterns)). | These are invocation/change events, not snapshots. The user and model paths require different hooks, and no hook enumerates all effective skills. Managed policy can restrict which hooks run. |
| **OTel `claude_code.skill_activated`** | One activation event for user slash, model-proactive, or nested invocation, with `skill.name`, `invocation_trigger`, `skill.source`, and optional plugin/marketplace fields ([event attributes](https://code.claude.com/docs/en/monitoring-usage#skill-activated-event)). This is the best supported deterministic source for a Claude Code skill invocation and its immediate trigger. | OTel must be enabled. User-defined and third-party names become `custom_skill` unless `OTEL_LOG_TOOL_DETAILS=1`. `skill.source` examples are documented, not a closed exhaustive enum. It observes use, not installed-but-unused skills. |
| **OTel tool events/traces** | With `OTEL_LOG_TOOL_DETAILS=1`, Skill-tool result/decision events and tool spans include the skill name; user-prompt events include command name/source ([OTel detail gate](https://code.claude.com/docs/en/monitoring-usage#common-configuration-variables), [tool-result parameters](https://code.claude.com/docs/en/monitoring-usage#tool-result-event), [user-prompt event](https://code.claude.com/docs/en/monitoring-usage#user-prompt-event)). | Direct user slash expansion bypasses the Skill tool, so Skill-tool events alone undercount. These are still usage signals, not inventory. |

For Agentlens terminology, `claude_code.skill_activated` can create a usage event without asserting successful application. `user-slash` supports initiator **user**, and `claude-proactive` supports initiator **model**. The source-owned schema also has `nested-skill`; Anthropic does not define that value in terms of Agentlens’s binary initiator model, so mapping it to user or model is an **unresolved product inference** and must not be silent.

## Lifecycle and change detection

- Claude Code watches `SKILL.md` under personal, project, and `--add-dir` skill directories and applies add/edit/remove changes during the session. If the top-level skills directory did not exist at session start, a restart is required. Plugin hooks, MCP, agents, and output styles require `/reload-plugins` ([live detection](https://code.claude.com/docs/en/skills#live-change-detection)).
- Added-directory command and agent files are not watched; their changes require restart ([additional-directory lifecycle](https://code.claude.com/docs/en/skills#skills-from-additional-directories)). `/reload-skills` and `SessionStart` hook output `reloadSkills: true` have been supported since [v2.1.152](https://github.com/anthropics/claude-code/releases/tag/v2.1.152).
- Plugin installs can activate immediately only when safe on current releases; otherwise `/reload-plugins` or restart is required. Before v2.1.221, every install needed reload/restart. Marketplace updates discovered after startup do not replace the running version until reload or the next launch ([plugin activation](https://code.claude.com/docs/en/discover-plugins#install-plugins), [plugin update lifecycle](https://code.claude.com/docs/en/discover-plugins#configure-auto-updates)).
- An invoked skill’s rendered body remains in conversation context for the session and is not re-read on later turns, even if the file changes; a later invocation can render updated content. Compaction preserves only budgeted portions of recent invoked skills ([skill-content lifecycle](https://code.claude.com/docs/en/skills#skill-content-lifecycle)). This affects behavior, but should not create or remove an installed-skill record.

## Managed-policy limits

Managed skills have highest plain-skill precedence, and managed settings outrank CLI, local, project, and user settings ([skill precedence](https://code.claude.com/docs/en/skills#where-skills-live), [settings precedence](https://code.claude.com/docs/en/settings#settings-precedence)). The decisive inventory controls are:

- Managed `strictPluginOnlyCustomization: ["skills"]` stops loading user/project skills, user/project legacy commands, added-directory skills, and synced skills, while keeping plugin, bundled, and managed-directory skills ([exact locked-surface behavior](https://code.claude.com/docs/en/settings-reference#strictpluginonlycustomization-skills)).
- `syncClaudeAiSkills: false` is deny-only and may come from user, local, or managed scope; a restrictive value wins, while `true` is equivalent to unset ([sync setting](https://code.claude.com/docs/en/settings-reference#syncclaudeaiskills), [precedence exception](https://code.claude.com/docs/en/settings#exceptions-to-managed-settings-precedence)).
- `disableBundledSkills`, `skillOverrides`, and `disableSkillShellExecution` change bundled presence, visibility, or runtime behavior, respectively; plugin skills are outside `skillOverrides`, and bundled/managed skills are outside `disableSkillShellExecution` ([skill settings](https://code.claude.com/docs/en/settings-reference#plugins-and-skills)).
- Server-managed settings are fetched at startup and polled hourly; macOS MDM is checked every 30 minutes; file-based managed settings reload on file changes. Cloud sessions receive server-managed policy, not the Mac’s MDM/file policy ([managed delivery cadence and surfaces](https://code.claude.com/docs/en/managed-settings#choose-a-delivery-mechanism), [policy reach](https://code.claude.com/docs/en/managed-settings#where-and-when-a-policy-applies)).

A collector that cannot inspect the winning managed source must report policy state as unknown. It must not promote a disk candidate to “available” merely because its file exists.

## Recommended supported boundary

For the expanded wayfinder map:

- **Version:** support the current documented behavior at v2.1.241 and require **v2.1.126+** only for the complete `claude_code.skill_activated` trigger contract. Feature-detect fields where possible; do not project current discovery rules backward without an immutable release note.
- **Installed-skill nodes:** accept source-attributed SDK/session observations as observed installations only when the source is actually exposed. Filesystem-only detections should be marked inferred candidates. Preserve agent client = Claude Code.
- **Usage:** prefer `claude_code.skill_activated`; count each event as one observed skill invocation and retain `invocation_trigger` and `skill.source` as raw evidence. Do not infer successful skill application.
- **Completeness flag:** every inventory observation should carry `complete: false` (or equivalent) until Anthropic publishes a passive effective-inventory API. Record at least Claude Code version, working directory, added directories if known, session ID/phase, and whether OTel detail logging was enabled.
- **Required gaps shown to users:** not-yet-traversed nested skills; model-only skills omitted by SDK init; hidden/disabled settings; managed-policy uncertainty; stale synced state; plugin trust/enable/reload state; bundled version drift; command-versus-skill ambiguity; and unresolved `nested-skill` initiator mapping.

## Negative finding and confidence

No complete passive effective-inventory command or API is documented in the current skills, Agent SDK, CLI, commands, hooks, OTel, plugin, settings, or managed-settings references cited above. This is a negative documentation finding, not proof that no undocumented internal mechanism exists. The public `anthropics/claude-code` repository provides release notes, docs, examples, and packaged releases, but not enough proprietary CLI implementation to independently audit its resolver. Agentlens should depend only on the supported documented surfaces and keep the inventory gap visible.
